# Restore Drill Runbook — isolated, disposable, evidence-producing

> **Status:** DEFINITION ONLY. No drill has been executed. `docs/trusted-ai/OPERATIONS_READINESS.md`
> records backup/recovery as **Untested**, and that claim stands until a drill completes
> against this runbook and its evidence checklist is filled in.

Backups that have never been restored are an assumption, not a capability. This runbook
exists so the first restore Teragon performs is a rehearsal, not an incident.

---

## 1. Safety boundaries (non-negotiable)

| Rule | Why |
|---|---|
| **Restore ONLY into a NEW, disposable Supabase project** created for the drill and deleted afterwards | A restore overwrites. There is no safe "restore on top of" |
| **NEVER restore into Production** | Absolute. No exception, no approval path in this runbook |
| **NEVER restore into active staging** (`bjvi…azjj`) | Staging carries the LIVE_VALIDATED customers/contacts evidence and the bootstrapped administrator; a restore would destroy the audit trail those claims rest on |
| **The drill is READ-ONLY against the restored copy** | The drill proves recoverability, not write behaviour |
| **NEVER create migration `015`** | Explicitly unauthorised repo-wide. A restore drill needs **no** schema change; if a drill appears to require one, that is a **stop condition**, not a licence |
| **No secret value is ever pasted, printed, echoed or committed** | See §3 |
| **No application deploy points at the drill project** | The drill project must never receive real traffic |

Migrations are and remain **14** (`001`–`014`). A drill that ends with a different count has failed.

---

## 2. Prerequisites

**Project**
- A brand-new Supabase project, created solely for this drill, in a non-production organization.
- A naming convention that makes disposal unambiguous: `teragon-restoredrill-<YYYYMMDD>`.
- Its region and Postgres major version should match the source; record both if they differ.

**Access**
- Permission to create *and delete* projects in that organization.
- The drill project's own service-role key — **generated by that project**, never reused from staging or Production.
- Supabase CLI authenticated for the drill project only.

**Source material (read-only)**
- The repository at a known SHA (record it).
- `supabase/migrations/001…014`, `supabase/seed/staging_seed.sql`, `supabase/tests/01…08`.

**Operator**
- One named operator, one named reviewer. The reviewer confirms §1 before any restore command runs.

---

## 3. Secret handling

Follows the conventions already proven in this repo:
- Credentials live only in a gitignored local env file; **never** committed, and `.env*.example` files carry **names only**.
- Secrets reach tooling via **stdin**, never argv, never a shell string, never a temp file.
- Logs and evidence record **presence and outcome only** — never a value, length, prefix, suffix or hash.
- Drill credentials are **revoked and the project deleted** at cleanup (§8).

---

## 4. Source backup / snapshot selection

Record before restoring:
1. **Snapshot identity** — backup/PITR timestamp in UTC.
2. **Source project** — masked ref only.
3. **Intended recovery point** and why (e.g. "15 minutes before a simulated destructive event").
4. **Backup mechanism** — platform automated backup, PITR, or `pg_dump` artifact.

If the snapshot cannot be identified unambiguously, **stop** (§9).

---

## 5. Schema and migration verification

Against the restored copy:
- [ ] Migration count is exactly **14**; no `015` present.
- [ ] Migration ledger matches `supabase/migrations/` names and order.
- [ ] `supabase db diff` (or equivalent introspection) reports **no drift** vs the repo at the recorded SHA.
- [ ] All expected tables exist, including `organizations`, `profiles`, `memberships`, `customers`, `contacts`.
- [ ] Indexes from `010_indexes.sql` present (notably `contacts.organization_id`, `contacts.customer_id`).

---

## 6. Security surface verification

- [ ] **RLS enabled** on every tenant table — an enabled-but-policyless table is a failure, not a pass.
- [ ] Policies from `012_rls_policies.sql` present with the expected capability mapping (e.g. `contacts` SELECT on `customer.read`).
- [ ] Helper functions from `011_rls_helpers.sql` present.
- [ ] Storage buckets and functions from `013_storage_and_functions.sql` present.
- [ ] **Auth**: `auth.users` restored; user count recorded; the administrator account exists and is email-confirmed.
- [ ] The 8 isolation checks (`supabase/tests/01…08`) pass against the restored copy — anonymous denial, cross-org read/write denial, membership-change denial, role-escalation denial, inactive-user denial, aggregate non-leakage, service-only bootstrap.
- [ ] **Row counts** per domain table captured and compared to the expected snapshot state; every discrepancy explained in writing.

---

## 7. Read-only application verification

- [ ] Point a **local** build at the drill project using its own publishable/anon key.
- [ ] Sign in as the restored administrator; confirm the canonical identity resolves (role + organization).
- [ ] Load `/customers`, a customer detail, and `/contacts` — **read only**.
- [ ] Confirm the health probes report the drill project as reachable with a working RLS read path.
- [ ] **Create/update/delete nothing.** No fixtures.

**RTO** — wall-clock from "restore initiated" to "read-only verification passed".
**RPO** — delta between the recovery point and the simulated incident time.
Record both as measured numbers; never estimate.

---

## 8. Cleanup and disposal

Cleanup is mandatory and runs even when the drill fails.
- [ ] Delete the drill Supabase project.
- [ ] Revoke/rotate any credential minted for the drill.
- [ ] Remove local env files and any downloaded dump artifact.
- [ ] Confirm no application configuration references the drill project.
- [ ] Confirm Production and staging were never targeted (§9 evidence).

---

## 9. Stop conditions, rollback, escalation

**Stop immediately** if any of these occur:
- A restore target resolves to Production or active staging.
- The snapshot cannot be identified, or its integrity is in doubt.
- Restore appears to require a schema change or a new migration (**never create `015`**).
- RLS is missing, disabled, or an isolation check fails.
- A credential is exposed in a log, terminal, ticket or commit.

**Rollback** is disposal: the drill mutates nothing outside the disposable project, so aborting means executing §8 and nothing else.

**Escalate** to the named reviewer with: the stop condition, the recorded evidence so far, and confirmation that §8 completed. Do not retry without a written correction.

---

## 10. Evidence checklist

A drill counts as performed only if all of this is recorded:

- [ ] Drill date (UTC), operator, reviewer
- [ ] Repository SHA under test
- [ ] Source snapshot identity and recovery point
- [ ] Drill project name (masked ref) and its creation + deletion timestamps
- [ ] Migration count = 14, no `015`, drift result
- [ ] RLS/policy/function/storage verification results
- [ ] Auth user count; administrator present and confirmed
- [ ] Isolation checks 01–08 outcome
- [ ] Per-table row counts and explanations for any discrepancy
- [ ] Read-only application verification result
- [ ] **RTO** and **RPO**, measured
- [ ] Cleanup confirmation (project deleted, credentials revoked)
- [ ] Explicit statement that Production and active staging were untouched
- [ ] Confirmation that no secret value, length, prefix or hash was printed

Only once every box is checked may `OPERATIONS_READINESS.md` move backup/recovery off **Untested**.
